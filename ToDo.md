* Year 2038: cTime inherits timeval, whose tv_sec is 32 bit long on Windows, cTime::Sec() returns long, and time columns in database are int(11) on all systems, for example reg_date, login_last, logout_last, date_start, date_limit and time, so cTime needs own 64 bit seconds instead of timeval, select() and cDCConf timers use tv_sec directly, and columns need upgrade to bigint
* Help languages: default help triggers always point to English %[CFG]/help_* files, share/config/ru is only copied and hub owner switches triggers manually with !modtrigger, when more languages exist, let --install point help triggers to language folder of chosen locale, ru files are CP1251, so they must be converted or skipped when locale charset is different, for example ru_RU.UTF-8
* Windows W6: portable folder with DLLs and their license texts next to exe, paths relative to exe, default configuration folder and install prefix, place of multi hub list verlihub.conf (now prefix/etc, maybe ProgramData), first run setup, locale names like en-US
* Windows W7: run as Windows service, CI that builds Windows zip, packages with CPack (deb, rpm, Windows zip), see todo in CMakeLists.txt
* IPv6: Verlihub has no IPv6 support yet, when it is added, also db_host in dbconfig needs [address]:port form
* SQLite: optional database instead of MySQL for small servers, CMake flag USE_SQLITE (default OFF), class cSQLite under cMySQL and cQuery, db_data in dbconfig is database file relative to configuration folder, db_host, db_user and db_pass are ignored, cConfMySQL writes SQLite syntax for escaping, upsert, table check and upgrade (no modify column, table is rebuilt), collate nocase on text columns so only A-Z are case insensitive like in hub, database thread uses own connection with WAL and busy timeout, Lua gets own SQLite calls and MySQL calls are not available, --install asks only for file, --backup and --restore write same SQL for both so MySQL hub can move to SQLite, !sysinfo shows sqlite3_memory_used()
* Binary text fields for MySQL: connection and text columns as binary, so bytes from socket are stored unchanged and db_charset is no longer needed, no MySQL collation folds only A-Z, so nick lookups need own key column folded by hub (see nick2dbkey todos in creglist.cpp, cpenaltylist.cpp and cbanlist.cpp), migration must convert stored data back with charset of old connection, check every column before changing anything, all tables of hub database including Lua script tables, check if binary is allowed as database default charset, phpMyAdmin shows binary as hex, scripts that compare nicks or use like become case sensitive, varbinary length is bytes not characters, migration risk to registered users is high, so postponed
* Connection lookups: CntConnIP (max_users_from_ip on login), GetConnByIP and GetConnUserByNick (scripts) walk all users or connections, an index by IP number and nick would need updates on connect, close, SetUserIP, SetSecConn, nick set at ValidateNick and for CntConnIP also on every class change, gain is small, so postponed
* Ban cache: new ban is added to index alone, but removing bans (unban, cleanup of old bans, reload) still builds whole index again, because positions in vector move, removal is rare and mostly manual
* CMake modules: own cmake/Modules/FindICU.cmake and FindLibintl.cmake could be replaced by FindICU and FindIntl that come with CMake 3.16, which is already minimum version, their result variables differ, so it needs testing on Linux, BSD and Windows MSYS2 before switching
* ZLib on worker threads: compression of user buffers runs on main thread and is one of biggest CPU users on big hub, worker would need copy of data, result back to same connection in same order before TLS encryption, later messages waiting behind it and handling of connection that closes meanwhile, measure CPU of zlib on real hub first, see todo in czlib.cpp
* Discardable bot messages: OnPublicBotMessage (VH_OnPublicBotMessage) is called after hub or bot chat is already sent to all, in DCPublicToAll, DCPublicHSToAll and triggers, so script can only watch, calling it before sending and discarding on false would block messages in old scripts that return false today, so it needs new separate callback, see todos in cserverdc.cpp and ctrigger.cpp
* ICU valgrind: valgrind shows uninitialized values around Transliterator::createInstance in cicuconvert.cpp, see todo there, ICU itself is known for such reports from loading its data, but it was not checked yet, how to debug: build with cmake -DDEFINE_DEBUG=ON, run hub in foreground with valgrind --track-origins=yes --num-callers=40 --log-file=valgrind.log verlihub -d <configuration folder>, transliterator is made when hub starts, so stop it with Ctrl+C after start, in valgrind.log look at every report that has cICUConvert in its stack, when line "Uninitialised value was created by" and frames below it are all inside libicu, report belongs to ICU and can be suppressed with --gen-suppressions=all, when it points to Verlihub code, our call is wrong
